Reference

      

        
Donut breakdown

        

          It isn't raytracing and there are no meshes. It's point-cloud splatting with a
          z-buffer: sample a parametric surface densely, project every sample into a
          character cell, keep the nearest, pick a glyph by lighting. About 28,000 samples a
          frame. That's the entire trick, and it's the whole reason this generalizes.
        

      

    


    

      

        
Think of it as spray-painting. The program never draws a donut. It picks about
        28,000 dots scattered over the surface of an imaginary donut, works out where each dot
        would land on a grid of text characters, and writes a character in that cell.

        
Which character? Whichever one looks like the right brightness — a dot facing the
        light gets a heavy @, a dot facing away gets a faint
        .

        
If two dots land in the same cell, the nearer one wins. That single rule is what makes
        the hole in the middle look like a hole instead of see-through. Then it turns the donut a
        few degrees and does the whole thing again, thirty times a second.

      

    


    

      
Two buffers

      
char  b[1760];   // 80 × 22 framebuffer, memset to 32 (space)
float z[1760];   // depth buffer, memset to 0 (= infinitely far)

      
80 × 22 = 1760. And memset(z,0,7040) is 1760 floats × 4 bytes — the one place the code admits how big a float is.

    


    

      

      
    


    

      

        
Spin, then flatten. Each dot gets rotated, then squashed onto the screen. Things
        farther away move toward the middle of the frame — that's all perspective is.

        
Two details that matter: the camera sits a fixed distance back so nothing ever ends up
        behind it, and the horizontal scale is doubled because text characters are about twice as
        tall as they are wide. Skip that second one and your donut is an oval.

      

      
Rotate, project

      

        Apply a rotation about X (angle A) then about Z (angle B).
        The code fuses both into three expressions and never names a matrix:
      

      
D = 1 / (c*h*e + f*g + 5);        // 1/z′  — z′ = ρ·sinφ·sinA + sinθ·cosA + K2
t =      c*h*g - f*e;             // the y-after-A-rotation intermediate
x = 40 + 30 * D * (l*h*m - t*n);  // K1x · perspective · Rz(B) applied to (ρcosφ, t)
y = 12 + 15 * D * (l*h*n + t*m);


      
Magic numbers

      

        
The original is full of unexplained numbers. Only four of them matter:

        
5 — how far back the camera sits. 30 and 15 — horizontal and
        vertical scale, doubled horizontally for the character shape. 40 and 12 — the
        middle of an 80×22 screen. 8 — stretches the brightness so it lands
        exactly on the 12 available characters, never past them.

Three angles

      

        
The rotation is three numbers. Dragging just changes them. There's no 3D scene to
        click into, no model to pick — which is exactly why drag was easy to add.

        
The original only had two of those numbers: tilt, and spin-like-a-wheel. Neither one
        turns a shape left and right, which a donut doesn't care about but a photo very much does.
        So there's a third one now. Sideways drag turns, vertical drag tilts, and letting go throws
        it.

      

      

        A and B are plain floats. Dragging just
        writes to them — no picking, no raycast, no scene graph, because there's no scene. That's
        the payoff of doing it in math instead of a 3D library.
      

      

        One catch: donut.c's two axes are pitch (about X) and roll (about Z), and roll
        spins the image in the screen plane. A torus is rotationally symmetric so nobody notices,
        but drag an imported photo sideways and it pinwheels instead of turning. So the prototype
        adds a third axis — yaw about Y, applied first:
      

      
var x0 = px * cc + pz * sc;   // Ry(C), the added axis
var z0 = pz * cc - px * sc;
// …then donut.c's Rx(A) and Rz(B), unchanged
var zp = py * e + z0 * g + dist;

      

        Four extra multiplies per point, and the same two lines run again on the normal so lighting
        follows. Horizontal drag → C, vertical drag →
        A. Release seeds a velocity that decays at 0.93/frame, then the
        auto-spin picks back up underneath it.
      


      
One dot product

      
How lighting works

      

        
Every dot knows which way it faces. Compare that direction to where the light is.
        Pointing at the light means bright, which means a heavy character. Pointing away means dark,
        which means a faint one. That comparison is a single multiply-and-add — it's the whole
        lighting model, and it's why the donut reads as a solid object rather than an outline.

      

      
int N = 8 * ((f*e - c*d*g)*m - c*d*e - f*g - l*d*n);

      

        A torus normal is just the cross-section direction, revolved:
        n₀ = (cosθcosφ, cosθsinφ, sinθ).
        Rotate it by the same A and B, dot with light L = (0, −1, −1),
        and you get that expression exactly. L is never normalized, which is
        why the result lands in [−√2, √2] and why the gain is 8.
      

      
b[o] = ".,-~:;=!*#$@"[N > 0 ? N : 0];   // N ≤ 0 = facing away → '.'


      
Output loop

      

        
It never clears the screen. It moves the cursor back to the top-left and types
        over what's already there. Clearing first is what causes flicker — for one instant
        you're looking at a blank frame. Overwriting in place has no such instant.

      

      
printf("\x1b[H");                      // cursor home, NOT clear → no flicker
for (k = 0; k < 1761; k++) {
    putchar(k % 80 ? b[k] : 10);       // every 80th char → newline instead
    A += 0.00004;
    B += 0.00002;
}

      

        
Column zero

        

          k % 80 ? b[k] : 10 spends column 0 on newlines — those cells are
          never printed. Which is why the clip test is x > 0 and
          y > 0, not ≥. The screen is really
          79 columns. Nobody notices.
        

      

      

        \x1b[2J (clear) fires once, before the loop. Per frame it's only
        \x1b[H — overwrite in place, so no tearing. Incrementing A and B
        inside the print loop is pure golf.

Real difference

        

          Your motion is 2D post-processing of a static grid. donut.c's motion is
          geometry moving in space, re-rasterized every frame. Closing that gap is
          the whole spike — and it slots in before your shading stage, so none of the good
          work gets thrown away.
        

      


      

        
You built the back half already. Turning brightness into characters, finding edges,
        picking colors, animating with noise — that's all done, and it's better than the
        original donut's version of it.

        
What's missing is everything before that: there's no shape, no camera, no sense
        of near and far. Your animation moves characters around a flat picture. The donut moves an
        object through space and re-draws it. Closing that gap slots in ahead of your existing work,
        so none of it gets thrown away.

      

      
Hardcoded presets

      

        kinetic.ts is 784 lines, and every look lives in a
        switch case — ocean_waves,
        flower_wind. Tuning means edit, save, wait for HMR, squint. No
        parameter surface, no way to A/B, no way to hand a look to someone else. The panel isn't a
        nice-to-have; it's what converts that switch into data.
      

    

  


  
  

    

      
Design

      

        
Architecture

        

          Every source emits the same PointCloud. After that the rasterizer
          doesn't know or care whether the shape came from a torus equation, an SVG path you drew,
          or a PNG you dropped on the canvas. That single contract is the methodology improvement.
        

      

    


    

      

        
One rule holds the whole thing together: every kind of input — an equation,
        a drawn shape, an uploaded photo — gets converted into the same plain list of dots.
        After that, the renderer has no idea where they came from and doesn't need to.

        
That's what makes it a tool instead of four separate demos. Add a new kind of input by
        writing one small converter; everything downstream already works.

      

      
src/lib/ascii/
  types.ts        Params, PointCloud, Frame
  sources/        shape → PointCloud
    parametric.ts torus / sphere — donut.c ported verbatim, the reference
    svgIngest.ts  DOM once → normalized polylines + arc length
    harmonics.ts  DFT → p(t) = Σ cₖe^(2πikt). the shape becomes an equation
    alphaMask.ts  PNG → marching squares → contour → same cloud
    heightfield.tsluminance → z displacement (this page's Image mode)
  raster.ts       transform → project → z-buffer → ramp
  post.ts         kinetic.ts layers, un-hardcoded into params
  render.ts       Uint16Array → one textContent write per frame


      
The contract

      
interface PointCloud {
  pos:   Float32Array;  // 3n — x, y, z
  nrm:   Float32Array;  // 3n — unit normal, for n·L
  alb:   Float32Array;  // n  — 0..1 source brightness (1 for parametric)
  arc?:  Float32Array;  // n  — 0..1 along-path position. this is the loader.
  count: number;
}

      

        arc is the field that turns a shape into a loading
        view. Reveal where arc < progress and it draws itself
        on. Scatter points by Perlin and lerp them home as progress →
        1 and it assembles. Both are about ten lines once the cloud carries arc-length —
        and neither one touches the rasterizer.
      


      
SVG paths

      
const path = document.createElementNS(SVG_NS, 'path');
path.setAttribute('d', d);
const L = path.getTotalLength();
for (let s = 0; s < L; s += spacing) {
  const p  = path.getPointAtLength(s);
  const p2 = path.getPointAtLength(s + 0.5);
  pts.push({
    x: p.x, y: p.y, z: 0,
    nx: -(p2.y - p.y), ny: p2.x - p.x, nz: 0,   // tangent → normal, free
    arc: s / L,
  });
}


      
Schema panel

      

        
The panel builds itself from a list. Each control is one line describing what it
        is — a slider from here to there, this label, this plain-English explanation. Adding a
        knob means adding a line, never building another slider component.

        
That's also why every control in the prototype has a hint under it. The hint is part of
        the control's definition, not an afterthought.

      

      

        Every parameter declares itself. The panel renders from the declaration, so adding a knob is
        one object literal — never a new slider component. Each one carries a plain-English hint, no
        graphics vocabulary required.
      

      
export const SCHEMA: Group[] = [
  { label: 'Camera', params: [
    { kind: 'range', key: 'spinX',      min: -2.5, max: 2.5, step: 0.02,
      label: 'Tumble — pitch', hint: "donut.c's A. Radians per second." },
    { kind: 'range', key: 'charAspect', min: 0.3,  max: 1.1, step: 0.01,
      label: 'Char aspect',   hint: 'Keeps circles round.' },
  ]},
  { label: 'Shading', params: [
    { kind: 'select', key: 'ramp',  options: RAMPS },
    { kind: 'vec3',   key: 'light', hint: 'Where the light comes from.' },
  ]},
];

      

        Values live in a mutable paramsRef.current, not React state — the
        rAF loop reads it directly, so dragging a slider never triggers a render. Same trick the
        panel on this page uses.
      


      

        
Preset export

        

          The tuned preset copies out as JSON and gets pasted into photos.ts
          as checked-in data. Playground output becomes production input, and the 784-line
          switch dies. That's the feature that makes this a tool rather than
          a toy.
        

      


      
Staying fast

      

        
No shaders needed. The rule is simple: build the list of dots once, reuse the same
        memory every frame, and write to the page exactly once per frame. Do that and 28,000 dots
        run at 60fps in ordinary JavaScript. The original ran in C on a 30fps budget — speed
        was never the hard part.

      

      
    
        
  • Point cloud in flat Float32Arrays, built once per shape — never per frame.
    • 
        
  • Pre-allocated Uint16Array charbuf and Float32Array zbuf, .fill() each frame. Zero allocation in the hot loop.
    • 
        
  • One textContent assignment per frame on a single <pre>. You already do this — keep it.
    • 
        
  • Sin/cos of the two spin angles computed once per frame, not per point.
    • 
        
  • The prototype above runs ~28k points at 60fps in plain JS. C on a 33fps budget was never the constraint.

Three SVG traps

      

      

        No viewBox. An SVG with only a viewBox and no
        width/height reports naturalWidth === 0 in some browsers, so
        drawing it to canvas silently produces nothing. Fix: parse it, write explicit dimensions,
        re-serialize, then load. An SVG with neither falls back to
        getBBox().
      

      

        Transforms. getPointAtLength() returns coordinates
        in the element's own user space, so a group with a transform lands
        in the wrong place. Every sample goes through getCTM() first.
      

      

        Untrusted markup. Measuring an SVG means putting it in the DOM, and a
        dropped file can carry <script> or
        onload=. The prototype strips executable elements, every
        on* attribute, and any href that isn't a fragment or a
        data:image/ URI before injection.
      


      
Two stages

      

        
Read the file once, then never look at it again. Opening an SVG and measuring its
        paths is slow and fiddly, so it happens a single time on import and produces plain lists of
        numbers. Every slider after that works on the numbers.

        
Before this, nudging any control re-opened the artwork from scratch. That's the thing you
        spotted, and it was the right call.

      

      

        The SVG DOM is touched exactly once, at ingest, and what comes out is
        typed arrays. Nothing downstream — no slider, no frame — ever looks at the uploaded markup
        again. Same shape of pipeline as the image path:
      

      
ingest  markup → sanitize → resolve viewBox → walk geometry
        → flatten at a fixed 0.5 SVG units → normalize to ±3
        → Float32Array polylines + cumulative arc length   ← DOM released here

build   polylines → resample → normals → extrude → PointCloud
        pure math, re-runnable every param change, zero DOM

      

        Ingest resolution is deliberately fixed and separate from
        spacing. Otherwise every nudge of a slider would re-enter the DOM,
        which is both slow and the thing you asked to avoid.
      


      
Algorithm or data

      

        
Two ways to remember a shape. Either you keep the list of points you traced
        — like a rubbing of a coin — or you find a formula that reproduces it, the way
        the donut has a formula.

        
For any closed outline, you can actually get a formula. The trick has a scary name
        (Fourier series) and a friendly idea: any loop can be drawn by stacking spinning
        circles. One circle draws a circle. Four circles draw a rough blob. Sixty-four circles
        draw your logo.

        
Which hands you a loading animation for free — start with a few circles and add
        more, and the artwork resolves out of a wobble. Try the Harmonics slider on the Path
        source above; that slider is the number of circles.

        
The one thing it can't do is fills. For solid artwork the next tool is called a distance
        field, which is also a formula rather than a picture, and which is what lets you thicken an
        outline or smoothly morph one logo into another.

      

      

        Straight answer: an arbitrary uploaded logo has no closed form. The torus has an
        equation because a person wrote one. Your asset is measurements. But that's not the end of
        it — there are three ways to hold a shape, and only one of them is really a bitmap:

              A grid of samples

Shape as equation

      

      

        Take a closed contour as a complex function of arc length,
        z(t) = x(t) + i·y(t), and run a DFT. Now the shape
        is a parametric equation — the same species of object as the torus:
      

      
// the donut
p(θ, φ) = ( ρcosφ, ρsinφ, sinθ )      ρ = R2 + cosθ

// your logo, after one transform
p(t) = Σ cₖ · e^(2πi k t)                  k = −K … K

      

        Both are evaluated, not looked up. Both give you a point at any t
        you ask for, at infinite resolution. The only difference is that the torus's coefficients
        were chosen by hand and the logo's were measured. Even the normal comes out analytically —
        differentiate the series instead of differencing neighbours:
      

      
dr -= pi * (6.283185 * k);   // d/dt of e^(2πikt) is 2πik·(…)
di += pr * (6.283185 * k);


      

      

        
Truncation

        

          Keeping fewer terms doesn't crop the shape, it smooths it. K=1 is a circle, K=4
          is a rough blob, K=64 is the asset. So the harmonic count is a loading
          animation — sweep K upward and the mark resolves out of a circle. Nothing else
          gives you that for free. Try the Harmonics slider on the Path source above.
        

      


      

        The catch, stated plainly: Fourier assumes a closed loop. An open stroke gets treated as
        closed, so the endpoints join and you get ringing near the seam. Fix is to mirror the path
        before transforming. Multi-contour logos are fine — each contour gets its own series.
      

      

        SDF is the one to reach for next, and it's the honest answer for filled
        artwork. A distance field is also evaluated rather than sampled, and it's what buys you
        thickness, erosion, boolean combination, and smooth morphs between two logos. It won't give
        you arc, so it complements the series rather than replacing it.
      


      

      
One-line reveal

      

        Once the cloud carries arc, the loading animation is a clip in the
        hot loop. Nothing else in the pipeline changes:
      

      
if (arc && arc[i] > P.reveal) continue;   // that's the whole loader

      

        Drive P.reveal from real progress and the mark draws itself on.
        Try it on the Path source above — the Reveal slider is that variable.
      

      

        Analysis should report what it found, because that's what picks the adapter: geometry
        element count, whether the alpha channel is meaningful, total path length, and the point
        count it would generate. Then the source choice is a two-option prompt, not a guess.
      

      

        New pane is worth building early. Two clouds, two param sets, one shared
        camera — that's how you compare a tuned preset against its parent, which is the thing the
        current edit-and-squint loop can't do at all.
